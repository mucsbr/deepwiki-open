# 业务流程文档生成方案

> 状态：方案讨论稿，未开始实施
> 最后更新：2026-09-22

## 1. 需求背景

### 1.1 原始需求

产品经理希望从前端某个按钮、某个页面操作，或某个 API 接口出发，生成**业务流程文档**——描述业务如何流转，而非展示代码实现。

### 1.2 真实问题

原始需求背后是更根本的问题：**四年技术债导致的知识断层**。

- 过去研发管理不规范，需求没有合规文档材料，没有技术评审
- 四年积累下来，新接手的团队缺少业务流程、产品功能清单等一切产品侧材料

### 1.3 关键约束（决定方案形态）

| 约束 | 影响 |
|---|---|
| **当事人全部离职，团队整体换新** | 无人可访谈，无人能校验 AI 产出 |
| **ToB 私有化部署，无线上数据** | 无法用调用量/PV 判断哪些功能真在使用，无法砍长尾 |
| 代码托管在 GitLab | 已有集成可复用 |

这两条约束排除了常规做法：既不能靠老员工口述补全，也不能靠埋点数据划定优先级。**代码成为唯一的一手事实来源。**

## 2. 现状能力盘点

基于对本项目代码的核查（非推测）：

### 2.1 已具备

- 仓库克隆、文件切分、向量化（`data_pipeline.py`）
- 单仓库 RAG 与跨仓库 RAG（`rag.py` / `multi_rag.py`）
- Wiki 生成（两条独立路径，见 `CLAUDE.md`）
- 结构化洞察抽取（`insight_extractor.py`：modules / endpoints / data_models / tech_stack）
- 仓库级依赖图（`repo_relations.py`）
- GitLab 集成、权限体系、批量索引、MCP 服务、Mermaid 渲染

### 2.2 核查发现的关键事实

**① 现有 wiki 是技术视角，不是业务视角**

`wiki_generator.py:_wiki_structure_prompt` 定义的章节为：

```
Overview / System Architecture / Core Features / Data Management /
Frontend Components / Backend Systems / Model Integration /
Deployment/Infrastructure / Extensibility
```

这是给工程师看的技术文档大纲。产品经理需要的是功能清单、业务规则、状态流转——**差异不是深浅，是视角**。

此外，现有章节按代码组织划分（前端/后端/部署），而业务流程是**横切**的（一个"退款"流程跨越前端、API、服务层、数据库、定时任务），现有划分方式天然切不出这种视图。

**② 项目的静态分析能力仅有正则**

`repo_relations.py` 的 `_extract_python_imports` / `_extract_js_imports` 是逐行正则匹配，且**显式跳过相对导入**：

```python
if pkg.startswith("."):  # skip relative imports
    continue
```

相对导入恰恰是项目**内部**的调用关系。现有实现只抓外部第三方包名，用于判断"仓库 A 是否依赖仓库 B"，从设计上就不是为追踪内部调用链而做。

后端依赖列表中无 `ast`、`tree-sitter`、`jedi` 等任何符号解析库。

**③ 克隆保留完整 git 历史**

`data_pipeline.py:192` 的 `git clone` 未加 `--depth`，完整历史可用。在当前约束下，这是少数仅存的信息源之一。

**④ 检索配置**

`embedder.json`：`top_k: 20`，`chunk_size: 350`，`chunk_overlap: 100`。

## 3. 技术路线的排除过程

讨论中曾走过几条路，记录结论以免重复论证。

### 3.1 排除：精确调用链追踪（LSP / tree-sitter）

**曾经的设想**：用符号解析构建精确调用图，再让 LLM 翻译成业务语言。

**排除理由**：

1. **本项目无 LSP 能力**（已核查确认，见 2.2②）。引入需从零搭建。
2. **tree-sitter 是单文件语法解析器**，不做符号解析、无跨文件概念。看到 `orderClient.create(...)` 只知道这是 `call_expression`，不知道 `create` 定义在哪。单仓库内需自建符号表，跨仓库是另一性质的问题。
3. **跨服务调用静态不可解**。微服务间靠 HTTP/RPC/MQ，两端在语法层面没有任何关联：

   ```python
   # 订单服务
   requests.post(f"{INVENTORY_URL}/api/v1/stock/deduct", json=payload)
   ```
   ```python
   # 库存服务
   @app.post("/api/v1/stock/deduct")
   ```

   任何分析器（tree-sitter、LSP、编译器）都跨不过去——这不是工具能力问题，是架构层面的信息缺失。

4. **决定性理由：无人可验证时，精度提升换不来可信度提升**。没有老员工能确认调用链是否正确，投入产出比不成立。

### 3.2 排除：更换为其他开源方案

见第 4 节调研结论。

### 3.3 保留：纯 RAG + 业务视角模板 + 防幻觉机制

理由见第 5 节。

## 4. 开源方案调研结论

调研范围：Reversa、flow-trace-genesis、DDS、RE-cue、OpenLore(spec-gen)、GitLab Duo、BPMN 工具、KoalaWiki。

### 4.1 核心结论

**没有任何现成方案能直接满足需求。继续改造本项目是正确选择。**

上述工具几乎全是 CLI 插件形态，依附于 Claude Code / Cursor 等 agent 运行，**没有一个提供**本项目已有的：GitLab 集成、权限体系、Web UI、批量索引、MCP 服务、缓存与渲染。它们的价值是**方法论**，不是替代品。

### 4.2 逐项评估

| 项目 | 数据 | 判断 |
|---|---|---|
| [sandeco/reversa](https://github.com/sandeco/reversa) | 1612★ MIT 活跃 | 成熟，但**目标读者相反**：产出是给 AI agent 的 operational contracts，README 明言 "not documentation for humans to read"。**置信度机制可直接借鉴** |
| [mthang1801/flow-trace-genesis](https://github.com/mthang1801/flow-trace-genesis) | 1★ Apache-2.0 | **需求最对口**：唯一把 PM 当一等读者、按角色分层输出。但 star 数极低，可靠性未经检验，**仅作设计参考** |
| [lucasacoutinho/dds](https://github.com/lucasacoutinho/dds) | 2★ MIT | fidelity-judge 抽样回查机制有价值，其余仅参考 |
| [cue-3/re-cue](https://github.com/cue-3/re-cue) | 5★ MIT | 强依赖 Spring Boot 注解（`@Transactional`/`@NotNull` 等），适用面窄 |
| [clay-good/OpenLore](https://github.com/clay-good/OpenLore) | 307★ MIT | **已转型**，现定位为 agent 记忆与护栏，不再是 spec 生成器 |
| GitLab Duo | 商业 | 需 Ultimate + Duo Enterprise 双授权；**官方无文档生成功能**，仅 Explain Code / Chat；输入上限 20 万 token。付费后仍需自写提示词 |
| BPMN 工具 | - | 全部只吃自然语言描述，**不吃源码**。现有 Mermaid 渲染已够用 |
| KoalaWiki | - | 同类替代品，迁移无额外收益 |

### 4.3 学术参考

[Reversa 论文](https://arxiv.org/html/2605.18684v1)（arXiv 2605.18684, CC BY 4.0）的方法论与本方案推导一致。

**但其证据强度有限，作者自陈**：案例仅一个教学用 ATM 系统（COBOL→Go），单一干系人，非生产环境；97.1% 置信度是流水线自评，无外部审计，"不应理解为事实精度"；专家精度与 agent 效用"未测量"，无对照基线。

**方法论可借鉴，不可作为效果承诺依据。**

## 5. 方案设计

### 5.1 核心定位

> **DeepWiki 的引擎够用，模板不够用。**

现有实现已完成最重的部分（克隆、切分、向量化、多轮生成、缓存、渲染、权限）。缺的是一套面向业务读者的提示词与配套校验机制。

**改动集中在提示词层，数据层与检索层不动。**

### 5.2 三项要借鉴的机制

#### ① 三档置信度标注（源自 Reversa）

强制 LLM 为每条结论标注依据等级：

- 🟢 **CONFIRMED** — 直接从代码提取，可验证
- 🟡 **INFERRED** — 从模式推断，可能有错
- 🔴 **GAP** — 无法确定，需人工验证

**这是本方案最重要的机制**。在无人可校验的前提下，诚实标注"不知道"比编造一个合理答案更有价值。

#### ② 业务视角模板（源自 flow-trace-genesis）

与现有技术模板**并存**，新增业务章节结构：

- 功能清单（按业务域划分，非代码结构）
- 核心业务流程（每个主流程一页，含 Mermaid 流程图）
- 业务规则与约束（条件、阈值、校验）
- 状态流转（状态机）
- 角色与权限
- 数据字典（业务对象，非表结构）

#### ③ 引用抽样回查（源自 DDS 的 fidelity-judge）

每条结论附 `file:line` 引用，生成后随机抽样回查被引代码是否支持该结论，判定 `WRONG_LINES` / `WRONG_FILE` / `HALLUCINATION`。

这是**无人校验条件下唯一可自动化的质量闸门**。

### 5.3 措辞纪律（写入提示词）

**描述行为，不解释意图。**

- ✅ 可写："点击提交后，订单状态从 A 变为 B，并写入 X 表"（行为，可从代码验证）
- ❌ 禁写："这样设计是为了保证幂等"（意图，是猜测）

### 5.4 改动范围

- `wiki_generator.py`：`_wiki_structure_prompt` / `_page_content_prompt` 增加模板分支
- `prompts.py`：前端驱动路径的对应提示词
- 新增：引用回查校验模块
- 模板选择参数需在两条生成路径上都接通（见 `CLAUDE.md` 的"两条 wiki 生成路径"）

## 6. 必须承认的局限

### 6.1 永久性缺失

**"业务为什么这么设计"大概率无法还原。**

不是"难查"，是"不存在"。没有人、没有文档，代码只记录 What 和 How，不记录 Why。为什么阈值是 15%、为什么多一道审核、这个分支是给哪个客户特批的——任何声称能还原意图的方案（包括 AI）都是在编造。

**建议**：把"还原业务意图"从目标中移除。能做到的是"准确描述系统当前行为"，这个目标低得多，但它是真的。

### 6.2 功能使用情况不可知

私有化部署导致无法得知哪些功能真被使用。代码库中的功能集合 ≠ 任何客户实际在用的集合。四年迭代必然积累大量死代码，纯从代码梳理会把它们全部当作"现有功能"写入文档。

### 6.3 静态分析的固有盲区

即使引入更强分析手段也抓不准的：运行时动态分发（反射、DI、事件总线、MQ）、跨服务 HTTP 调用、配置驱动的分支（feature flag、工作流引擎配置）、前端组件层事件传递。

### 6.4 最大风险：虚假确定性

**无人校验时，AI 生成的业务文档若被当作权威，危害大于没有文档。**

没有文档时，人知道自己不知道，会去问人、看代码。有了一份看起来专业、实际掺杂猜测的文档后，人会停止怀疑——而两年后没人分得清哪些经过考证、哪些是模型编的。这会形成新的、更隐蔽的技术债。

**因此 5.2① 的置信度标注和 5.2③ 的引用回查不是可选项，是前提条件。**

## 7. 尚未利用的信息源

当前约束下仍可挖掘，按价值排序：

1. **Git 历史**（完整保留，最被低估）
   - commit message：四年变更记录，含需求编号、bug 描述
   - MR / Issue 讨论：**最接近"当事人对话"的遗留物**
   - 代码时间分布：三年未改动的模块要么稳定要么已死
   - GitLab API 已在用（`api/v4/projects` 等），增加 MR/Issue 拉取改动不大

2. **数据库 Schema**
   表结构是业务概念最诚实的映射，状态枚举基本即业务状态机。且不受代码死活影响。

3. **客户环境数据库统计**
   私有化部署意味着客户处有真实运行的库。若能取得脱敏后的**各表行数统计**，即可部分替代线上数据用于砍长尾。属流程问题而非技术问题，值得争取。

4. **部署配置与运维脚本**
   配置开关、feature flag、定时任务表，可反映哪些功能实际启用。

**Git 考古是 AI 用得最安全的场景**——它在总结已有文本，而非推测代码意图，幻觉风险最低。

## 8. 实施步骤

### 阶段一：最小验证（建议起点）

1. 新增业务视角模板（5.2②）
2. 提示词加入三档置信度标注 + `file:line` 引用（5.2①、5.3）
3. 拿本项目自身跑通，与现有技术 wiki 对比

**验证目标**：确认"业务模板"是否确为产品经理所需，再决定后续投入。

本项目具备代表性：有前端按钮、后端多跳流程（`admin.py` → `batch_indexer.py` → `wiki_generator.py` → `insight_extractor.py`）、异步任务。

### 阶段二：质量闸门

4. 实现引用抽样回查（5.2③）
5. 输出置信度报告与 gap 清单

### 阶段三：扩展信息源

6. Git 历史 / MR 讨论接入
7. 数据库 Schema 接入

### 阶段四：配套机制（非技术）

8. 新需求强制文档与评审，堵住新增技术债
9. 新人接手模块时以 AI 初稿为起点、实跑系统验证并修正

## 9. 待确认事项

| 问题 | 影响 |
|---|---|
| 目标系统是单体还是微服务？ | 单体则跨仓库问题不存在，方案简化一半 |
| 是否有 OpenAPI/Swagger 或 proto 文件？ | 有则跨服务链路可走契约而非猜字符串 |
| GitLab 的 MR/Issue 讨论是否还在？ | 这是当事人留下的唯一痕迹 |
| 能否搭起可运行环境？ | **硬前提**。无环境则新人无法验证任何产出，文档可信度非常有限 |
| 能否取得客户环境的表行数统计？ | 替代线上数据的唯一途径 |
| 是否存在客户定制分支？ | 影响"功能集合"的定义 |
